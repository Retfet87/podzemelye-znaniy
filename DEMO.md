# Изолированный демонстрационный режим

Состояние после стабилизации: код, seed/cleanup/rollback/concurrency и права demo-роли проверены на отдельной native PostgreSQL 16.9. Loopback HTTP подтверждает allowlist и hot disable. Docker-сети/образ/entrypoint и настоящий MAX пока не проверены; до них не считать окружение готовым к показу. Точный отчёт — [VALIDATION.md](VALIDATION.md).

Демо не меняет работу основного `main.py`. Отдельные `compose.demo.yml`, PostgreSQL, том, сеть, роль `demo_app`, seed и `demo_bot.py` используют только demo-настройки. Не объединять demo Compose с основным `docker-compose.yml`. Не копировать рабочий `.env`, токен или резервную копию реальных персональных данных в demo.

## Что сохранено и что защищено

- Все 32 карточки исходного `seed_useful.py` из kruto сохранены в `fixtures/demo/useful.json`, явно помечены как вымышленные. Телефоны заменены неактивными заглушками.
- `seed_useful.py --apply/--remove` теперь безопасная обёртка; никаких fallback на `DATABASE_URL` или `TEST_DATABASE_URL`. Для наполнения только «Полезного» XLS не нужен.
- `seed_demo.py --demo` создаёт задания и мероприятия после загрузки разрешённого публичного расписания в отдельную demo-БД. Синтетический demo_user не является реальным MAX-аккаунтом. Живые разрешённые аккаунты регистрируются в demo-БД отдельно; личное задание синтетического пользователя им недоступно.
- `seed_akvt.py` перенаправляет в тот же безопасный demo seed и больше не читает рабочую конфигурацию.
- Проверяются фиксированные имя demo-БД/роль, допустимый адрес, отсутствие libpq overrides и предварительно созданный маркер среды. Без маркера ни seeding, ни миграции demo не начинаются. Маркер принадлежит bootstrap-роли, у приложения только чтение.
- Idempotent seed использует транзакцию/блокировку и стабильные ключи fixtures; совпадение названия с чужой карточкой не присваивает её demo. Очистка касается только отмеченных ID. Demo-расписание не удаляется seed-очисткой.
- DemoRouter допускает только личные диалоги аккаунтов из allowlist. DemoClient ограничивает адресата текущим аккаунтом, callback текущим запросом, добавляет баннер «ДЕМО» и префикс имени файла. Все demo-аккаунты видят общий набор внутри отдельной demo-среды; со студентами основного бота он не смешивается.
- Фоновый worker в demo_bot не создаётся; общий worker дополнительно отказывается работать при наличии demo-маркера. Флаги уведомлений не отменяют этот запрет.

## Подготовка без запуска MAX

Нужен Docker Engine с Compose. Эти Docker-команды здесь НЕ выполнялись; SQL provisioning отдельно проверен через psycopg на новом native-кластере.
Создать отдельный локальный `.env.demo` (игнорируется Git), с отдельными паролями; DSN не должен содержать рабочие credentials. Пример структуры, значения заменить:

```dotenv
DEMO_OWNER_PASSWORD=REPLACE_WITH_SEPARATE_OWNER_PASSWORD
DEMO_DB_PASSWORD=REPLACE_WITH_SEPARATE_APP_PASSWORD
DEMO_DATABASE_URL=postgresql://demo_app:REPLACE_WITH_SEPARATE_APP_PASSWORD@demo-postgres/podzemelye_demo
DEMO_ENABLED=0
DEMO_POLLING_ALLOWED=0
DEMO_ALLOWED_USER_IDS=
DEMO_BOT_TOKEN=
```

Пароль в URL должен быть URL-encoded при наличии специальных символов. Не сохранять заполненный файл в Git и не выводить `compose config` с секретами. Начальная сеть БД internal, порт на хост не публикуется. Demo-роль не superuser и не создаёт другие базы/роли. Отдельные пароли и том обязательны; маркер не заменяет инфраструктурную изоляцию.

```sh
docker compose --env-file .env.demo -f compose.demo.yml -p podzemelye-demo-review config --quiet
docker compose --env-file .env.demo -f compose.demo.yml -p podzemelye-demo-review up --build demo-setup
docker compose --env-file .env.demo -f compose.demo.yml -p podzemelye-demo-review run --rm demo-seed python seed_useful.py --apply
```

Для трёх мероприятий/заданий сначала загрузить отдельную копию разрешённого XLS:

```sh
docker compose --env-file .env.demo -f compose.demo.yml -p podzemelye-demo-review run --rm -v /ABSOLUTE/PUBLIC-SCHEDULE.xls:/input.xls:ro demo-seed python seed_demo.py --demo --xls /input.xls
```

Автоимпорт разрешён только в пустую demo-БД. Поэтому полный seed с `--xls` нужно делать до useful-only seed. Если useful-only уже был выполнен, очистить его через `seed_useful.py --remove`, затем выполнить полный seed. Рабочее расписание и рабочий `manage.py migrate` не использовать.

Очистка только demo-карточек: та же команда `run` с `python seed_useful.py --remove`. Очистка полного набора: `python seed_demo.py --demo --clean`. Она сохраняет импортированное расписание и неотмеченных пользователей/карточки.

## Выключатель

Для разрешённого запуска отдельного demo-бота одновременно нужны:

1. Отдельный тестовый токен `DEMO_BOT_TOKEN`, явное разрешение запуска `DEMO_POLLING_ALLOWED=1` и `DEMO_ENABLED=1`.
2. Непустой список конкретных MAX ID `DEMO_ALLOWED_USER_IDS`, через запятую без пробелов.
3. Файл `demo-control/enabled` с точным содержимым `1` и переводом строки; папка монтируется read-only в `/run/demo`. До первого запуска папку создаёт оператор с правами чтения для UID 10001.

Рабочий токен сюда не подставлять. Live-профиль не запускается ни setup, ни seed. Команду запуска demo-live применять только после отдельного разрешения и проверки, что это другой бот; в этой сессии poller не запускался.

Мгновенно закрыть доступ: записать `0` с переводом строки в `demo-control/enabled` или удалить файл. Следующие входящие запросы/исходящие ответы будут запрещены без рестарта и без удаления данных. Уже отправленные сообщения и скачанные файлы не отзываются. Чтение файла выполняется каждый раз; отсутствие/ошибка закрывает доступ. Сам polling после выключения может продолжать получать обновления, но содержимое demo не выдаёт; для остановки процесса остановить только отдельный demo-bot сервис.

## Проверки

`PYTHONDONTWRITEBYTECODE=1 python -m scripts.test_offline` не читает рабочий `.env`, исключает реальные DB-настройки и выполняет доступные unit-тесты. DB suites пропускаются намеренно; пропуск не означает успешную проверку изоляции PostgreSQL.

До показа обязательны на disposable PostgreSQL: schema migrations, два последовательных и два конкурентных seed, очистка при совпадающих названиях, отсутствие очередей, запрет demo_app изменять маркер, недоступность другой БД/сети, повторный запуск контейнера и проверка Docker build context. Затем — отдельно разрешённый телефонный прогон MAX с тестовым токеном. Не утверждать выполнение этих проверок без фактического результата.

Demo Compose не запускает mini-app: его отдельный вход описан в [WEB.md](WEB.md). Автоматический deploy, аккаунтный demo внутри production-процесса и автоматический backup demo отсутствуют. Обычный main.py теперь отказывается от demo-БД до создания MAX-клиента. Это выбранная отдельная среда, а не глобальный флаг для всех студентов.
