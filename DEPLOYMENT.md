# Запуск и демонстрация

Нужны Docker Engine и Docker Compose v2. Для проверки контейнеров используй отдельный проект Compose и пустой токен MAX.

## Изолированная проверка

`sh scripts/check_docker.sh` собирает образ, применяет миграции и запускает полный набор тестов с имитацией MAX, затем отдельный сквозной smoke-test. После этого сохраняет пользователя, черновик и два вида вложений, пересоздаёт контейнеры, проверяет данные, делает one-shot и scheduled архивы PostgreSQL и восстанавливает каждый в отдельную базу. Скрипт создаёт собственный проект Compose и очищает только его тестовый том. Токен MAX пустой, сервис Long Polling выключен. Этот же сценарий запускается в GitHub Actions. Тесты реального XLS в контейнере пропускаются, если файл не передан; локально их нужно выполнить с `AKVT_TEST_XLS`.

Отдельный сквозной тест запускается одной командой из корня проекта:

```sh
TEST_DATABASE_URL=postgresql://user:password@127.0.0.1:порт/podzemelye_test python -m scripts.smoke_test
```

Предварительно создай пустую отдельную базу с именем `*_test` или `*_demo` и установи зависимости проекта. Сценарий не читает `.env` и рабочий токен. Он создаёт случайную схему и удаляет только её после проверки: регистрация через роутер и кнопки, группа, расписание, личное задание с файлом, запись на мероприятие, формирование напоминания без отправки, повторное открытие данных новым роутером и соединениями. Настоящее пересоздание контейнеров и восстановление архива проверяет `check_docker.sh`.

Тесты реального XLS дополнительно доступны локально.

```sh
AKVT_TEST_XLS=/полный/путь/расписание.xls \
TEST_DATABASE_URL=postgresql://user:password@127.0.0.1:порт/отдельная_база \
python -m unittest discover -s tests -v
```

## Контейнеры

```sh
cp .env.docker.example .env.docker
chmod 600 .env.docker
# Задай новый POSTGRES_PASSWORD в .env.docker.
docker compose --env-file .env.docker -p podzemelye-demo config --quiet
docker compose --env-file .env.docker -p podzemelye-demo up -d --build migrate
docker compose --env-file .env.docker -p podzemelye-demo logs migrate
```

Для существующего тома сохрани прежние POSTGRES_DB, POSTGRES_USER и пароль. Настройки инициализации PostgreSQL применяются только к пустому тому. Именованный том `pgdata` хранит регистрации, расписание, задания, мероприятия и вложения в PostgreSQL. Сохраняй имя проекта `-p` между запусками. Обычный `down` сохраняет том. `down --volumes` удаляет данные.

Создание групп и предпросмотр XLS выполняются через существующий CLI. Для файла с компьютера передай `-v "$PWD/расписание.xls:/input.xls:ro"` команде `docker compose run`, затем `migrate python manage.py inspect-schedule /input.xls`. Для публикации нужен явный подтверждённый период и команда супер-администратора из этапа 4.

После подготовки данных для отдельного демонстрационного MAX-бота укажи его токен и свой MAX ID в `.env.docker`. Включение Long Polling выполняется явно.

При переносе существующего рабочего бота сначала нужна свежая резервная копия рабочей базы с проверкой восстановления. Не запускай контейнер с тем же токеном одновременно с прежним экземпляром. Остановка прежнего процесса и включение нового требуют отдельного подтверждения владельца; автоматическая проверка и PR этого не делают. Профиль `live` сам не является блокировкой. Новый процесс удерживает отдельную PostgreSQL-сессию с advisory lease по хешу токена; второй процесс с этим токеном в той же базе откажется запускаться. Lease проверяется до/после MAX poll и перед обработкой события, потеря соединения останавливает poller. Между разными базами/серверами эта защита не действует: один токен должен использоваться ровно в одном согласованном развёртывании. Lease занимает одно дополнительное прямое соединение вне пула.

```sh
docker compose --env-file .env.docker -p podzemelye-demo --profile live up -d --build
docker compose --env-file .env.docker -p podzemelye-demo --profile live logs --tail 20 bot
```

TLS проверяет доверенную цепочку и имя сервера. Корневой сертификат MAX входит в образ. Секреты и резервные копии исключены из контекста сборки.

## Резервное копирование

```sh
mkdir -p backups
BACKUP_UID="$(id -u)" BACKUP_GID="$(id -g)" \
docker compose --env-file .env.docker -p podzemelye-demo run --rm backup
```

Скрипт записывает архив в скрытый временный файл, проверяет его каталог через `pg_restore --list` и только затем переименовывает. При ошибке архива нет в списке готовых копий. Проверка реального восстановления входит в изолированный Docker-тест. Архивы содержат личные данные и должны храниться с ограниченным доступом.

Ручная проверка восстановления выполняется только в новую отдельную базу. Замени `ИМЯ.dump` именем готового архива; `restore_check` не должна существовать. Команды не подменяют рабочую базу и не удаляют её:

```sh
docker compose --env-file .env.docker -p podzemelye-demo exec -T postgres sh -c 'createdb -U "$POSTGRES_USER" restore_check'
docker compose --env-file .env.docker -p podzemelye-demo exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d restore_check --exit-on-error' < backups/ИМЯ.dump
docker compose --env-file .env.docker -p podzemelye-demo exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d restore_check -c "SELECT count(*) FROM schema_migrations; SELECT count(*) FROM users; SELECT count(*) FROM homework_files; SELECT count(*) FROM useful_files;"'
```

Ненулевой код восстановления — ошибка, такую копию нельзя считать проверенной. В автоматическом сценарии дополнительно сверяются байты вложений. Обычная команда создаёт одну копию. Ни ежедневный режим, ни ротация в рабочей среде не включались; отдельный режим описан ниже. В Compose нет отдельного файлового тома: содержимое вложений находится в PostgreSQL и включено в дамп.

## Показ на хакатоне

1. С тестового аккаунта открой `/start`, выбери направление и группу, покажи расписание на неделю.
2. Создай личное задание без срока, добавь небольшой TXT и открой его из карточки.
3. Супер-администратор создаёт явно помеченное демонстрационное мероприятие, проверяет предпросмотр и публикует. Участник нажимает «Пойду», повторяет нажатие, проверяет счётчик и отменяет участие.
4. Покажи реальную проверенную ссылку в «Полезном» и редактирование карточки.
5. Перезапусти только демонстрационные контейнеры и открой прежнее задание с файлом. Флаги рассылки для показа можно оставить выключенными.

Заполнение неподтверждёнными сведениями о кабинетах, мероприятиях и контактах заменено безопасным `seed_akvt.py --demo`. Он создаёт один помеченный черновик только в отдельной TEST_DATABASE_URL с суффиксом имени базы `_test` или `_demo`. Сценарий показа работает и без этого скрипта.

Перед выпуском пройди [чек-лист MAX](MAX_CHECKLIST.md). Автоматические проверки не заменяют проверку внешнего интерфейса MAX.

## Ежедневные копии — только после отдельного разрешения для рабочей среды

Профиль `scheduled-backup` выключен по умолчанию. `backup-daily` делает первую копию сразу, следующую через 86400 секунд после завершения предыдущей. После обычного рестарта отсчёт начинается заново; это простой интервальный scheduler, не календарный cron с выполнением пропущенных запусков. Дамп создаёт `backup.sh`, проверяет каталог и атомарно переименовывает. Файлы только в `backups/scheduled-v1`, с маркером владельца; существующая папка без маркера не принимается. `.lock` предотвращает второй scheduler. После аварийного завершения возможен оставшийся lock: оператор сначала убеждается, что scheduler остановлен, и только затем вручную убирает пустую папку lock. Автоматического удаления lock нет.

Для отдельного тестового проекта, после создания `backups` с правильным владельцем:

```sh
BACKUP_UID="$(id -u)" BACKUP_GID="$(id -g)" \
docker compose --env-file .env.docker -p isolated-backup-check --profile scheduled-backup up -d backup-daily
```

Не менять имя `-p` у существующей среды; пример выше предназначен для нового тестового проекта. Переменная `BACKUP_ROTATION_ENABLED=0` сохраняет все копии. Значение `1` явно разрешает оставить семь файлов, созданных scheduler в его отмеченной папке; старые `backups/*.dump` не затрагиваются. При одинаковой секунде имена сортируются по случайному суффиксу, поэтому порядок внутри секунды не определяет точный последний файл. Не включать ротацию на рабочей среде без отдельного подтверждения владельца. Unit-тесты проверяют отказ/частичный архив, сохранность старых копий и opt-in ротацию; настоящий pg_dump/restore — только изолированный Docker-сценарий. Состояние выполненных проверок — VALIDATION.md.

Backup содержит формы и вложения, не токен из `.env`; сам `.env` хранить отдельно в защищённом хранилище. Нет внешнего облачного хранения и уведомлений об отказе scheduler. Ежедневность нужно контролировать по логам и времени последних проверенных архивов. Проверять восстановление периодически на отдельной PostgreSQL; не считать один только `pg_restore --list` достаточным.

## Два отдельных продукта — финальная версия 8 ноября

Обычный бот запускается как прежде; его Dockerfile, PostgreSQL и миграции не превращены в хостинг анонимного API. Самостоятельный публичный сайт — папка `demo-site/`, данные — `fixtures/demo/site.json`; он не использует MAX Bridge, регистрацию или PostgreSQL. `web/` и `mini_app.py` остаются отдельной защищённой заготовкой: без подписи API отвечает 401, режим `local` не включается. Для текущего публичного сайта mini_app.py не нужен.

### Сборка и локальная репетиция сайта

```sh
python -m scripts.build_demo_site
python -m http.server 8088 --bind 127.0.0.1 --directory dist
```

Сборщик копирует только перечисленные публичные файлы, проверяет demo-набор, не читает `.env`, не подключается к базе и не запускает MAX. Не указывать корень репозитория как каталог веб-сервера. Для сборки не нужны Node/npm и серверные секреты; `node scripts/test_frontend.mjs` нужен только для дополнительных тестов интерфейса. Неизвестные файлы или симлинки в каталоге сборки приводят к отказу, а не к их публикации/удалению. Используйте пустой каталог либо прежний чистый `dist`.

### Размещение по HTTPS

1. Выбрать с владельцем уже согласованный статический хостинг. Внешний аккаунт, публикацию и изменение доступа без его подтверждения не выполнять.
2. Собрать сайт и загрузить **содержимое `dist/`**, включая `data/` и `assets/`, а не репозиторий и не рабочую папку. Поддерживаются размещение в корне и подкаталоге: все внутренние пути относительные. Секреты, роли БД, MAX ID и токен для сайта не требуются.
3. Корень должен отдавать index.html; JS/CSS/JSON/PNG/SVG/MP4/TXT/ICS — правильные MIME-типы. Хостинг должен поддерживать загрузку MP4, желательно byte ranges. Рекомендуемые заголовки: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; CSP с `default-src 'self'` уже в HTML. Не добавлять сторонние аналитические/авторизационные скрипты.
4. Проверить HTTPS на реальном телефоне: четыре вкладки, 32 материала и категории, прошлый отчёт, воспроизведение видео, скачивание TXT/.ics, две темы. Открытие сайта не должно требовать MAX, ChatGPT, GitHub или чужую сессию. Если хостинг закрыт логином — это ещё не публичная демонстрация.
5. После подтверждённой публикации можно задать **переменную окружения** `PUBLIC_DEMO_SITE_URL` обычного бота (в Compose поле уже передаётся). Только проверенный публичный HTTPS без query/токена. Без неё кнопка сайта скрыта, старый callback отвечает понятным текстом и не предлагает localhost. Изменение окружения рабочего процесса потребует согласованного перезапуска; эта разработка его не выполняет.

Сайт read-only, кроме пробных действий в памяти вкладки. Это не запись на настоящее событие и не облачное хранение заданий. Все изменения сбрасываются после перезагрузки. Данные учебной недели 9–14 ноября — явно вымышленные, не обновляются с сайта АКВТ. Фото — иллюстрация, видео — пример MDN, источники в CREDITS.md сборки. Публикация обычного HTML не подключает MAX mini-app и не должна включать анонимный доступ к защищённому API.

### Финальные проверки

`review/**` запускает Actions на push; также добавлена проверка pull_request. Workflow выполняет 8 JS-сценариев, собирает публичный сайт, затем запускает прежний изолированный Docker/PostgreSQL/smoke/recreate/backup/restore. На Mac Docker отсутствует: его статус подтверждается только Actions. База/вложения/очереди бота остаются в pgdata; статический сайт не нуждается в резервной копии рабочих персональных данных.

В этой итерации миграции не добавлялись: актуальная схема 001–007. Для старой рабочей базы по-прежнему обязательны свежая копия, проверка восстановления и отдельное разрешение на изменение/переключение. Не выполнять команды live из инструкции как часть теста сайта.
