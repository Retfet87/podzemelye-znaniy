# Подземелье знаний

Учебный бот для студентов Астраханского колледжа вычислительной техники. Работает на Python 3.12 и получает события MAX через Long Polling.

Первый `/start`: приветствие с иллюстрацией → «🏫 АКВТ» → направление → группа. Регистрация хранится в PostgreSQL. Повторный вход показывает сохранённую группу. Во вложенных разделах есть «🏠 Домой»; выход из незавершённой формы подтверждается без публикации. Прежние регистрации сохраняются миграцией.

Навигация, медиа мероприятий, теги, история и безопасное демонстрационное наполнение описаны в [UX_DEMO.md](UX_DEMO.md).

## Структура проекта

Код лежит в пакете `app/`, разложенном по слоям: `max_api` (клиент MAX), `db` и `repositories` (PostgreSQL), `services` (логика без ввода-вывода), `handlers` (реакции на события), `notifications` (фоновая очередь). Точки входа остались прежними: `python main.py` и `python manage.py`. Подробности и схема — в [ARCHITECTURE.md](ARCHITECTURE.md).

## Локальный запуск на macOS

Для уже подготовленного окружения на этом Mac запусти PostgreSQL из папки проекта, если он ещё не запущен:

```sh
.runtime/postgres-16/bin/pg_ctl -D .runtime/postgres-data -l .runtime/postgres.log -w start
```

База слушает только `127.0.0.1:55432`. На другой машине можно использовать [Postgres.app или другой пакет PostgreSQL для macOS](https://www.postgresql.org/download/macosx/). Создай отдельную локальную базу `podzemelye` и пользователя с паролем, который владеет этой базой. Например, при доступе к локальному серверу от имени администратора:

```sh
createuser --pwprompt podzemelye
createdb --owner=podzemelye podzemelye
```

Если окружение Python ещё не настроено, выполни:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
```

Файл `.env.example` показывает формат настроек. В существующем `.env` сохрани токен и путь к сертификату. Для нового окружения добавь `MAX_BOT_TOKEN` и `DATABASE_URL` вида `postgresql://podzemelye:ПАРОЛЬ@127.0.0.1:5432/podzemelye`, указав свой порт. Если в пароле есть специальные символы URL, закодируй их. Пароль и токен хранятся только локально; `.env` исключён из Git.

```sh
.venv/bin/python manage.py migrate
.venv/bin/python manage.py add-groups "Название первой группы" "Название второй группы"
.venv/bin/python main.py
```

В команду добавления групп передай реальные названия; каждое название с пробелами возьми в кавычки. Список из примера вводить не нужно. Миграции можно запускать повторно, уже применённые файлы пропускаются. Для остановки бота нажми **Ctrl+C**. Чтобы остановить локальную копию PostgreSQL, выполни `.runtime/postgres-16/bin/pg_ctl -D .runtime/postgres-data -w stop`.

## MAX и TLS

Токен передаётся в заголовке `Authorization`. Бот получает сообщения и нажатия кнопок через [`GET /updates`](https://dev.max.ru/docs-api/methods/GET/updates), отправляет клавиатуру через [`POST /messages`](https://dev.max.ru/docs-api/methods/POST/messages) и подтверждает выбор через [`POST /answers`](https://dev.max.ru/docs-api/methods/POST/answers/). Для Long Polling не должно быть активного Webhook. Не запускай два процесса опроса одного бота одновременно.

Для `platform-api2.max.ru` MAX [требует доверенный сертификат Минцифры](https://dev.max.ru/docs-api). `MAX_CA_FILE=certificates/russian_trusted_root_ca.pem` добавляет корневой сертификат в контекст соединений бота с MAX. Проверки цепочки и имени хоста включены. Относительный путь считается от папки проекта; при недоступном или некорректном файле бот не запускается. Источник сертификатов: [Госуслуги](https://www.gosuslugi.ru/crt).

## Проверки

```sh
.venv/bin/python -m unittest discover -s tests -v
```

Тесты API имитируют ответы MAX. Интеграционные проверки PostgreSQL запускаются при заданной `TEST_DATABASE_URL` в `.env` или в окружении. Используй отдельную локальную базу для тестов. Тесты создают и удаляют временные схемы внутри неё. Можно проверить диалог вручную: отправь `/start` в личном чате, нажми кнопку группы, затем снова отправь `/start`. Последний ответ должен содержать сохранённую группу и главное меню. Повтори после перезапуска бота, чтобы проверить сохранение выбора.

## Этап 3. Расписание АКВТ

Импорт рассчитан на четырёхстрочную сетку из [XLS АКВТ](https://www.akvt.ru/wp-content/uploads/2026/11/bolshoe-raspisanie-p-2609-1-7.xls). Команда разбора выводит группы, число записей по типу недели и примечания без подключения к БД.

```sh
XLS="$HOME/Downloads/bolshoe-raspisanie-p-2609-1-7.xls"
.venv/bin/python manage.py inspect-schedule "$XLS"
.venv/bin/python manage.py migrate
```

Верхняя половина разделённой горизонтальной чертой ячейки трактуется как числитель, нижняя как знаменатель. Пока понедельник недели-числителя неизвестен, бот показывает оба варианта с подписями. Загрузка новой версии описана в этапе 4 ниже.

Для проверки в личном диалоге MAX отправь `/start`. На новом аккаунте выбери реальную группу из XLS, например **ПБ-22** или **ИБ-11**. На зарегистрированном аккаунте повторный `/start` открывает меню с сохранённой группой. Затем нажми **Расписание → Сегодня → Завтра → Неделя → Назад**. «Неделя» показывает текущий понедельник–воскресенье. Даты определяются в `Europe/Samara`, часы взяты из [расписания звонков АКВТ на 2026–2027](https://www.akvt.ru/wp-content/uploads/2026/09/soglasovano-2.png). Проверь, что в пределах срока действия воскресенье показывает «Занятий нет», а за пределами срока появляется сообщение о незагруженном расписании. Для аккаунта из тестовой группы без данных появится то же сообщение о незагруженном расписании.

```sh
AKVT_TEST_XLS="$XLS" .venv/bin/python -m unittest discover -s tests -v
```

Тесты используют `TEST_DATABASE_URL` и создают временные схемы PostgreSQL. Проверка реального файла ожидает конкретный XLS по ссылке выше.

## Этап 4. Обновление расписания

1. Останови бота, сделай резервную копию рабочей БД и выполни `.venv/bin/python manage.py migrate`. Миграция `003_schedule_updates.sql` добавляет черновики, историю изменений и очередь. Версии этапа 3 считаются базовыми. Регистрации сохраняются.
2. Укажи в локальном `.env` значение `MAX_SUPER_ADMIN_ID` своего аккаунта. Роль действует только для отправителя с этим ID в личном диалоге. При пустом значении команды публикации отключены. Локальная подготовка XLS доступна оператору, у которого есть доступ к файлу проекта и БД.
3. После проверки на отдельном боте установи `SCHEDULE_NOTIFICATIONS_ENABLED=1` и запусти бота. По умолчанию отправка из очереди выключена. Подтверждённые обновления всё равно накапливают задания. Перед включением проверь очередь командой `.venv/bin/python manage.py notification-status`.

### Предпросмотр и подтверждение

Сохрани XLS на диске. Для базового расписания явно задай период, включая обе границы. Если известен понедельник недели-числителя, передай его через `--numerator-monday`. Если в пересекающейся действующей версии понедельник уже задан, укажи его явно.

```sh
.venv/bin/python manage.py import-schedule "$XLS" --scope base \
  --from "$VALID_FROM" --to "$VALID_TO" --numerator-monday "$NUMERATOR_MONDAY"
```

Команда показывает по датам и группам добавления, отмены и изменения, включая прежние и новые значения. Сверь с утверждённым расписанием. Для базового черновика сверь отдельно количество групп и строк XLS. Повтори команду с `--stage --expect-groups "$GROUP_COUNT" --expect-lessons "$LESSON_COUNT"`. Если в предпросмотре есть утверждённые отмены, также укажи их точное число через `--expect-cancellations N`. Число считается по датам и вариантам недели из предпросмотра. Программа блокирует базовый файл при несовпадении состава групп с последней версией, пустой группе или падении числа строк в группе более чем на 20%. XLS с неизвестным предметом в выбранной области также блокируется. Изменение состава групп требует отдельного согласованного процесса.

Для замены в один день укажи дату и одну или несколько групп через повторяющийся `--group`. Используется **целый день выбранной группы** из XLS, поэтому отсутствующие пары считаются отменами. Замена имеет приоритет перед последующими базовыми версиями только в эту дату. Если день в базовом расписании содержит две неподтверждённые версии по типу недели, сначала подтверди понедельник числителя в базовом расписании. Когда тип недели нужен только для входного XLS, укажи `--numerator-monday` для замены.

```sh
.venv/bin/python manage.py import-schedule "$XLS" --scope date \
  --from "$CHANGE_DAY" --group "ИБ-11"
```

Для черновика повтори команду с `--stage` и сверенным числом отмен при необходимости. Предпросмотр без `--stage` доступен и для прошлых дат. Черновики создаются для текущих и будущих дат. Изменения вступают в силу после `/schedule_confirm КОД` в личном диалоге супер-администратора. `/schedule_cancel КОД` отменяет черновик. Код действует 30 минут и устаревает, если за это время опубликована другая версия. Повтор команды подтверждения не создаёт новую версию или рассылку. Для повторного XLS без изменений черновик не создаётся.

Очередь создаёт по одному сообщению на пользователя для каждой публикации с видимыми изменениями в его группе. Задания сохраняются при перезапуске. Очередь повторяет временные ошибки до пяти попыток, учитывает числовой `Retry-After` при 429, ограничивает отправку и записывает исход каждой попытки в текущий статус, счётчик и последнюю ошибку. При смене группы и после завершения затронутого периода сообщение пропускается. Если MAX принял сообщение, но подтверждение потерялось, при повторной попытке возможен дубль. Лимиты и адресация описаны в [документации MAX](https://dev.max.ru/docs-api/methods/POST/messages).

### Проверка в MAX на тестовой группе

1. Возьми отдельную локальную БД, отдельный MAX-бот и тестовые аккаунты. Храни тестовые настройки в отдельной копии проекта с собственным `.env`. Оставь отправку выключенной. Примени миграции и подтверди исходный XLS до регистрации тестовых аккаунтов.
2. Через `/start` выбери для первого тестового аккаунта **ИБ-11**, для второго любую другую группу. В копии XLS измени кабинет одной пары ИБ-11. Выбери дату, которую можно открыть через «Сегодня», «Завтра» или «Неделя».
3. Запусти предпросмотр замены на дату. Проверь, что видна ровно ожидаемая правка, в очереди ничего нет, а в MAX показывается прежний кабинет. Создай черновик и отмени его. Проверь очередь и расписание снова.
4. Создай второй черновик. Попробуй подтвердить его с обычного аккаунта, затем подтверди с супер-администратора. Проверь новый кабинет в выбранный день и одно задание в очереди. Включи отправку, перезапусти тестового бота и проверь, что сообщение приходит только аккаунту из ИБ-11, а в сводке появляется `sent: 1`. Повтори подтверждение и импорт, чтобы проверить отсутствие новой рассылки.

## Этап 5. Домашние задания

Открой личный диалог с ботом и нажми «Домашние задания» после /start, отправь /homework или напиши дз / домашка.

- Студент видит общие задания своей группы и может создавать, редактировать и удалять собственные личные задания. Личные задания и их файлы доступны только владельцу.
- Администратор группы управляет её общими заданиями. Супер-администратор управляет общими заданиями всех активных групп и назначает или снимает администратора в меню группы. Для назначения нужен MAX ID уже зарегистрированного участника этой группы.
- Предметы берутся из расписания выбранной группы. Можно оставить задание без срока. Срок указывается в формате `ДД.ММ.ГГГГ ЧЧ:ММ` по времени Самары.
- Прикрепляй PDF, PNG, JPG или UTF-8 TXT как файлы, до трёх по 5 МБ. Скачивание доступно из карточки задания. После предпросмотра нажми «Сохранить». Черновик хранится в текущем процессе до 30 минут.

Миграция `004_homework.sql` добавляет таблицы заданий, прав, вложений и очереди домашних заданий. Рабочую базу перед обновлением следует скопировать и проверить восстановление. Затем выполни `.venv/bin/python manage.py migrate` и перезапусти бота.

Для автоматической отправки установи в локальном `.env` параметр `HOMEWORK_NOTIFICATIONS_ENABLED=1`. Он управляется отдельно от рассылки расписания. Очередь использует тот же отправитель MAX, ограничение частоты и повторные попытки. Напоминания о заданиях со сроком отправляются за 24 и 3 часа, с доставкой в оставшейся части соответствующего окна после перерыва в работе бота. Смена срока исключает ожидающие напоминания о прежнем сроке. Уведомления о новых общих заданиях и напоминания можно отключить отдельно в меню «Уведомления».

Для проверки в рабочем MAX оставь отправку домашних заданий выключенной и создай только личное задание без срока. Проверь создание, повторное открытие, вложение, редактирование и удаление. Для проверки рассылки используй отдельную базу или автоматические тесты с подменой MAX.

## Этап 6. Мероприятия и полезные материалы

В личном диалоге отправь `/start` и выбери «Мероприятия» или «Полезное». Также доступны `/events` и `/useful` и текстовые триггеры (мероприятия, события, полезное, материалы, кураторы, преподаватели). В обоих разделах доступна кнопка «Назад» для возврата в главное меню.

- Супер-администратор сохраняет черновик мероприятия, проверяет его и отдельно подтверждает публикацию. Предложения администраторов групп попадают в «Черновики и предложения» с названием группы. Публикация, изменение и отмена доступны супер-администратору.
- Зарегистрированный студент видит предстоящие опубликованные мероприятия и число участников. «Пойду» записывает аккаунт один раз, «Не пойду» снимает запись. Дата и время показываются по Самаре.
- В «Полезном» пять категорий. Супер-администратор добавляет общие материалы, администратор группы добавляет и редактирует материалы своей группы. Студенты видят общие материалы и материалы своей группы. Можно сохранить текст, HTTPS-ссылку или до трёх файлов PDF, PNG, JPG или UTF-8 TXT по 5 МБ. Для публикации используется предпросмотр. В рабочей базе категории исходно пусты; реальные материалы публикуются через предпросмотр. Демо-наполнение допускается только в отдельной изолированной среде; Переключаемое демо-окружение описано в [DEMO.md](DEMO.md); его Docker/PostgreSQL-проверки ещё не выполнены.

Миграция `005_community.sql` добавляет мероприятия, записи, задания на отправку и материалы. Перед миграцией рабочей БД сделай резервную копию и проверь восстановление. `EVENT_NOTIFICATIONS_ENABLED=1` включает отправку участникам через общий обработчик очереди. Напоминание становится доступно за 24 часа, а при поздней записи — до начала мероприятия. Изменение даты обновляет напоминание. Отмена исключает прежние напоминания. При потере подтверждения MAX повтор доставки возможен.

Для проверки в основном MAX открой оба раздела, просмотри список и категории, пройди форму до предпросмотра и отмени действие. Проверяй RSVP и доставку уведомлений на отдельной БД с имитацией MAX. В рабочей базе тестовые мероприятия публиковать не требуется.

## Этап 7. Запуск и проверка

Основной и единственный источник актуальных инструкций контейнерного запуска, резервного копирования, восстановления и демонстрации — [DEPLOYMENT.md](DEPLOYMENT.md).

- `sh scripts/check_docker.sh` проверяет Docker на отдельном томе без запуска MAX Long Polling.
- `TEST_DATABASE_URL=... python -m scripts.smoke_test` выполняет сквозной сценарий на отдельной локальной базе с именем `*_test` или `*_demo`, без чтения рабочего токена и настоящих сообщений.
- Резервные копии создаются явной командой. Автоматические ежедневные копии и ротация не настроены.
- `seed_demo.py --demo` требует явный `DEMO_DATABASE_URL` и маркер отдельной demo-БД; создаёт помеченные примеры без рассылки. Непроверенные контакты и кабинеты не публикуются.

Серая заливка XLS трактуется как «Другой корпус» только с явным `--gray-other-building` после проверки легенды расписания.

Перед объединением и переключением рабочего экземпляра пройдите [чек-лист MAX](MAX_CHECKLIST.md). Само наличие успешных тестов не запускает рабочий бот.
