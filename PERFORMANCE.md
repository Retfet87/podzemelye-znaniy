# Производительность и стабильность

## База до изменений

Измерения исходного кода `ab090f2`, без пула. Это локальный эксперимент, не SLA и не прогноз для сервера/MAX.

Среда: Python 3.12.16, PostgreSQL 16.9, arm64, 8 логических CPU. Новый отдельный кластер, loopback TCP + SCRAM, ограниченная роль и bootstrap-owned validation-маркер. Рабочая конфигурация не читалась.

Синтетические данные: 100 студентов, 1 группа, 18 недельных строк расписания, 1 общее задание, 1 событие без медиа. Mock MAX записывает ответы, не имеет сетевого транспорта. Каждый сценарий начинает с отдельного Database; seed/provisioning исключены из времени.

10 и 50 запросов выполняются последовательно, 100 — в ThreadPoolExecutor с 8 потоками. Три сценария: зарегистрированный /start, просмотр недели, карточка мероприятия. Реальный Long Polling остаётся последовательным: конкурентный сценарий проверяет общий router/repositories только на этих операциях, не формы и не пропускную способность MAX.

Задержка включает обработчик и ответ mock-клиенту; p95 — ближайший ранг ceil(0.95*n). Время партии включает очередь executor, закрытие Database измеряется отдельно. Физические соединения считаются от успешного connect до close; максимум включает все установленные соединения. Отдельного monitor-соединения нет. SQL — вызовы execute, включая служебные операции. ## Подтверждённые узкие места

- /start: 3 подключения и 4 SQL-вызова на пользователя: регистрация/группа, расписание, сроки заданий.
- Неделя: 1 подключение и 1 запрос.
- Карточка события: 6 подключений и 6 запросов. event вызывается повторно через details и media, детали читаются повторно. Это не N новых пользовательских функций, а повтор существующих проверок видимости. Их удаление требует сохранения ACL и согласованности, поэтому нельзя просто убрать вызовы.
- Mini-app homework/events в ReadViews использует ограниченный N+1 по карточкам (до 8 на страницу). Это вывод просмотра кода, не результат указанного нагрузочного сценария. Оптимизация прав не входит в этот небольшой эксперимент.
- Ошибка обработчика уже изолирована в Router (d8dfd4f); fatal MAX 401 не поглощается. Формы содержат mutable in-memory state, поэтому вводить параллельный production polling по этим замерам нельзя.
- Worker удерживает session-level locks через commit во время отправки. Обычный connection.close освобождает их; наивный возврат в пул этого не делает. Требуется очистка сессии до повторного использования.

## Решение после базовых замеров

Оправдан небольшой ограниченный opt-in пул на уровне Database с сохранением with db.connect(). Нужны тесты commit/rollback, повреждённых соединений, session locks и закрытия. До них пул не считается готовым. Никаких пользовательских кэшей, новых workers или изменения polling concurrency не вводится.

Полные исходные числа: [validation/performance-before.json](validation/performance-before.json). Воспроизведение: PERFORMANCE_DATABASE_URL=... python -m scripts.performance --output result.json; требуется отдельная заранее подготовленная *_test база с маркером. Скрипт владеет только собственной случайной схемой и удаляет её после завершения.


## Реализация пула

`Database(..., pool_size=N)` сохраняет `with db.connect()` и закрывается через `close()`/контекст Database. `DB_POOL_MAX_SIZE=0` по умолчанию оставляет прежний прямой режим; явное значение 1–16 включает ограниченный пул обычного бота после будущего согласованного перезапуска. Измеряется N=4; это размер эксперимента, не универсальная рекомендация. Очередь ожидания ограничена 32, ожидание — 5 с. CLI, mini-app и demo автоматически на пул не переведены; DemoDatabase явно запрещает его, сохраняя per-connection marker checks.

Адаптер через публичные getconn/putconn и Connection context завершает транзакцию, затем синхронно выполняет DISCARD ALL вне транзакции до повторной доступности сессии. Это снимает все session advisory locks, сбрасывает настройки/роль, temp/протокол LISTEN и prepared statements. Автоматическая подготовка отключена только на pooled connections, чтобы DISCARD ALL не рассинхронизировал кэш psycopg. Ошибка reset/сломанная сессия приводит к удалению соединения, а не выдаче следующему пользователю. Проверка соединения перед выдачей включена. Сессионные блокировки уведомлений по-прежнему удерживаются через commit во время отправки.

Основание: [psycopg pool lifecycle](https://www.psycopg.org/psycopg3/docs/advanced/pool.html), [PostgreSQL 16 DISCARD](https://www.postgresql.org/docs/16/sql-discard.html). Тесты проверяют commit, rollback, SQL error, timeout, закрытую сессию, провал reset, повторные locks через commit, temp/search_path, два worker pool и shutdown. Новая миграция не требуется; работающая конфигурация не изменяется.


## Закрытый контроль работоспособности

Опциональный `BOT_HEALTH_FILE=/private/operator-directory/health.json` включает локальные snapshots и SELECT 1 каждые 30 с. Каталог заранее создаётся владельцем с 0700; файл атомарно записывается с 0600. Symlink/чужой владелец/открытые права отвергаются. Файл содержит PID, время успешного MAX poll (в том числе пустого), последнее DB probe/доступность, счётчик изолированных ошибок обработчиков и фиксированную категорию critical failure. Содержимое запросов, MAX ID, credentials и DSN туда не попадают. Demo-режим и web-сервер не изменены.

Чтение только владельцем ОС: `python -m scripts.health /private/operator-directory/health.json`. Код выхода 0 — процесс жив, свежи MAX/DB проверки, нет critical/stopped; 1 — degraded/старые проверки/остановлен; 2 — файл недоступен или неверные права/формат. `--max-age 120` — явная настраиваемая политика свежести диагностики, не задним числом выбранный performance SLA. Печатаются возраст проверок и snapshot. DB-status означает последнее probe, а не запрос CLI к рабочей БД.

MAX 401/фатальная ошибка, непредвиденный выход main loop и смерть notification worker видимы как critical. Ошибка одного обработчика учитывается отдельно и не останавливает следующий update. Отказ записи snapshot не ломает обработку событий; старый snapshot становится несвежим. При нормальной остановке ставится stopped, потоки завершаются перед закрытием пула. Это не supervisor и не автоматический restart. Отключённый по умолчанию health не создаёт поток/файл; работающий процесс и его .env не менялись.


### Пограничные случаи возврата

При первом pooled-замере инструментальный счётчик не учёл уничтожение PGconn без вызова Python close. Счётчик дополнен учётом уничтожения и независимой сверкой pg_stat_activity после завершения (вне измеряемой нагрузки). Неверный прогон не использован как результат.

Дополнительно ДО исправления воспроизведены два дефекта: изменённый autocommit передавался следующему borrower; немедленный close мог оставить возвращённую сессию открытой, если вызывающий код сохранил ссылку и асинхронный reset ещё не выполнился. Вместо фонового callback выбран небольшой синхронный контекст: commit/rollback → DISCARD ALL → восстановление autocommit/row_factory/isolation/read_only/deferrable → putconn. Ошибка очистки закрывает сессию; KeyboardInterrupt не поглощается. Две регрессии проверяют именно сохранённую ссылку и изменённые Python-настройки, а не только серверные GUC. Это не изменение репозиториев или concurrency polling.

### Интерпретация и ограничения

- 100 конкурентных /start: создано 300 → 4 физических соединения; карточка события: 600 → 4. Ограничение 4 соблюдено, ошибок нагрузки 0. Последовательные сценарии итогового синхронного адаптера создали по одному соединению.
- Шесть прикладных чтений карточки события сохранены. SQL-вызовов стало больше из-за проверки соединения и DISCARD ALL: например, 600 → 1800 при 100 карточках. Пул экономит установку соединений, а не устраняет N+1 или повторные ACL-проверки.
- Прогон однократный для каждой комбинации, на общем desktop, без доверительного интервала. Нет настоящих MAX HTTP/TLS, внешнего сетевого времени и медиа; нельзя переносить эти цифры на полный отклик бота или заявлять production throughput.
- В каждом сценарии пул начинает пустым: холодная первая установка видна в хвосте короткой серии. В сравнении с ПЕРВЫМ baseline p95 недели при N=10 вырос с 4.853 до 5.450 мс; прямой повторный контроль дал 7.614 мс. Среднее улучшилось, но универсальное улучшение каждого p95 не заявляется.
- Повторные проверки авторизации и ограниченный N+1 mini-app остаются. Целесообразна отдельная оптимизация разрешённой пакетной выборки после измерения именно web workload; в этой задаче она не вводилась.
- Production polling остаётся последовательным. Долгий SQL, ожидание advisory lock или отправка MAX по-прежнему могут задержать обработку следующих событий. Query timeout/новый executor без согласованной политики не добавлялись. Потокобезопасность форм/черновиков не доказана и не требуется для выбранных read-only сценариев.
- Минимальный health не является supervisor: он не перезапускает процесс и не отзывает уже отправленные сообщения. Это opt-in диагностика владельца, со своей настройкой свежести.
- Новые функции demo/mini-app не переизобретались. Повторный cold restore и Docker не выполнялись: код хранения/формат архива не менялись, предыдущая проверка восстановления описана в VALIDATION.md. Новая регрессия проверяет восстановление соединений/транзакций, не выдаётся за новый restore архива.

Полные pooled-числа: [validation/performance-after.json](validation/performance-after.json). Примеры воспроизведения:

```sh
PERFORMANCE_DATABASE_URL=... python -m scripts.performance --output direct.json
PERFORMANCE_DATABASE_URL=... python -m scripts.performance --pool-size 4 --output pooled.json
```

Оба запуска требуют отдельной ограниченной роли и bootstrap-owned validation-маркера, не используют .env, создают и удаляют только свою случайную схему. Настройка пула передаётся в Compose как DB_POOL_MAX_SIZE с нулём по умолчанию; health-каталог в контейнер автоматически не публикуется/не монтируется.

## Финальные проверки и границы

Финальный набор: 184 обнаружены, 183 успешно, 1 пропущен, 0 ошибок. Пропуск — реальный MP4 без ffmpeg. Включены исходные 156 тестов, 16 тестов pool и 12 тестов health/lifecycle. Выполнены миграции на изолированной PostgreSQL (в том числе через пул размера 1), demo guard/role/seed rollback/cleanup, loopback HTTP mini-app authorization/scope, уведомления и два workers, обрыв backend, reset failure, сохранённая ссылка на возвращённый conn и восстановление клиентских настроек. Синтетические MAX-ответы не являются реальной проверкой MAX.

Ruff E4/E7/E9/F по затронутым файлам, Python/shell/YAML syntax и git diff --check проверены. Системное ПО не устанавливалось; psycopg_pool 3.3.3 установлен только в отдельное task-venv. Рабочие настройки, PostgreSQL, процесс бота и прежние backup не менялись. Push/merge/deploy не выполнялись. Docker runtime/MAX/iOS/Android не проверялись этой задачей.

Дополнительно: аудит закреплённых зависимостей с новым psycopg_pool не нашёл известных уязвимостей. Это проверка известных advisory, не доказательство отсутствия всех дефектов. Новый performance-кластер остановлен после сверки SHOW data_directory; данные и предыдущие резервные копии сохранены. Для будущего включения требуется отдельное разрешение на restart/deploy; по умолчанию оба механизма выключены.
