### P0.3 Деморежим: сначала отдельное окружение

## 7. ТЗ P3 — стабильность без опасной оптимизации

2. Pool: сохранить with db.connect(), ограничить размер и время ожидания, закрывать при shutdown.

   закрытием соединения. Возврат в пул не снимает сессионные блокировки, включая ранние return.
   До пула добавить освобождение всех взятых locks в finally; сбойный reset → discard connection.
   Не заменять бездумно транзакционными locks: send_job делает commit перед внешней отправкой.
   Тесты конкурентных workers, отказов/ранних выходов, повторного использования соединения,
   rollback, насыщения пула. Проверить pg_locks; исключить зависание и двойную доставку.
3. Health: отдельные liveness/readiness; heartbeat успешного polling с учётом long-poll timeout,
   готовность БД/схемы и состояния worker. HTTP 200 без проверки цикла не считать healthcheck.
   Docker healthcheck сам по себе не перезапускает unhealthy контейнер: нужен явный supervisor
   или завершение зависшего процесса с последующим restart. Проверка только на тестовом боте.
4. Drafts: JSON-схема с version, TTL 30 мин, actor/environment/kind/token/revision;
   ограниченные проверенные вложения отдельно, атомарная смена состояния и optimistic lock.
   Не pickle. Тест после рестарта, TTL, удаления вложения, устаревшей кнопки, чужого actor.
   Миграция разрабатывается и испытывается только на disposable PostgreSQL.
5. Backup: ежедневный запуск в отдельном сервисе, блокировка параллельного backup,
   проверка/атомарное завершение, ротация 7 успешных копий; неполные архивы не заменяют успешные.
   Restore в НОВУЮ пустую тестовую БД: миграции, счётчики и сценарий чтения/записи.
   Не выводить пароли и не удалять файлы за пределами выделенного каталога.
6. Load: 100 синтетических акторов, dummy MAX sender, disposable PG с известными fixture.
   Отдельно последовательная dispatch-нагрузка и параллельные repository-запросы;
   общий Router с in-memory DraftStore не объявлять потокобезопасным без проверки.
   Записать железо/версии/данные, concurrency, ошибки, p50/p95/max, соединения/locks.
   Цель проекта p95 <1 с без реальной MAX-сети — гипотеза, а не требование/гарантия жюри.

## 8. ТЗ P4 — небольшие интеграции

ICS: только доступное пользователю расписание/событие, корректные UID/DTSTAMP/DTSTART/DTEND,
TZID или UTC, CRLF, escaping запятых/точек с запятой/обратных слэшей/переносов,
folding по 75 октетам без разрыва UTF-8. Demo помечать в SUMMARY/DESCRIPTION.
Тесты стандартным парсером, Unicode, повторным экспортом и пустым списком;
реальный импорт в календарь телефона — отдельная ручная отметка.

XLS: переиспользовать существующий parser → preview → stage → ручное подтверждение;
автозагрузку не публиковать автоматически. Супер-администратор, лимит размера/строк/времени,
проверка формата, временный файл с безопасным именем, cleanup. При скачивании — allowlist
официального host/path, HTTPS, ограниченные redirects с повторной проверкой адреса,
запрет private/loopback/link-local IPv4/IPv6 для защиты от SSRF и DNS rebinding.
Хеш источника, diff, защита от повторного stage, отказ от подозрительной потери групп/пар.
Тесты malformed/oversized файла, redirect/SSRF, дублей, чужой роли и отсутствия публикации.

Реестр разделов разрешён лишь после доказанной потребности; не требуется для mini-app/ICS.
